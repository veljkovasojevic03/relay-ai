# Decisions

One line per decision: what + why. Newest at the bottom of each phase.

## Phase 0: Foundation

- **Next.js 16.4 with `cacheComponents` on** (create-next-app default). Dynamic route handlers opt out of prerendering with `await connection()`; this matches where Next is heading.
- **pnpm 12, Node 24** (`.nvmrc`, `engines`). Current LTS. pnpm 12 `allowBuilds` makes every install script an explicit choice: only `supabase` (CLI binary download) is allowed.
- **No pnpm workspace yet: the Next.js app stays at the repo root (`src/app`) instead of `app/`.** The spec allows a workspace "only if it stays simple". The widget gets its own esbuild build in Phase 5 without needing a second package manifest.
- **Repo layout:** `src/` (app), `widget/`, `supabase/` (config, migrations, functions), `n8n/`, `eval/`, `docs/`, `scripts/`, `e2e/`. Folders that a later phase fills hold a short README naming that phase, not fake code.
- **Env names follow spec §10 exactly.** `NEXT_PUBLIC_SUPABASE_ANON_KEY` also accepts Supabase's newer publishable key and `SUPABASE_SERVICE_ROLE_KEY` the newer secret key; both drop into the same slots.
- **All integrations are optional in the env schema**; features check `has*()` helpers and degrade (Sample mode, simulated n8n, billing off). This enforces the "graceful fallback, no fake stubs" rule.
- **`N8N_MODE` defaults to `simulated` unless `N8N_WEBHOOK_BASE` is set; `real` without base + secret fails at boot.** A misconfigured real mode should fail loudly, not silently simulate.
- **Live (`sk_live_`) Stripe keys are rejected at boot.** The $0 / Hobby-plan rule must be impossible to break by misconfiguration.
- **Env validation errors list variable names and rule messages, never values.** Avoids leaking secrets into logs.
- **Structured JSON logger with flat scalar fields only.** Makes it hard to accidentally log message bodies or objects containing PII.
- **Baseline security headers now (nosniff, referrer, `SAMEORIGIN`, permissions policy); strict dashboard CSP later**, once the third-party origins it must allow exist. `SAMEORIGIN` rather than `DENY` so the landing page can frame `/demo`.
- **`/api/health` calls `public.health_check()` (`select now()`) through the service-role client.** It is a real Postgres round-trip that touches no tables and is executable by `service_role` only. It returns 200 `degraded` when Supabase isn't configured (local/CI) and 503 only when a configured database fails.
- **Cron: GitHub Actions hourly at :17 → `POST /api/cron/tick` with `Authorization: Bearer CRON_SECRET`.** Hourly is far inside the 7-day pause window and leaves headroom for outbox retries later. Unauthorized → 401; no secret configured → 503 (never open). The workflow skips cleanly when repo secrets are missing.
- **Bearer secrets are compared via SHA-256 digests + `timingSafeEqual`.** Equal-length buffers mean no length or content timing leak.
- **i18n: next-intl with locale-prefix routing, `localePrefix: "as-needed"`** (English at `/`, Serbian at `/sr`). Prefix routing keeps pages statically prerenderable under Cache Components (cookie-based locale would make every page dynamic) and keeps `/demo` clean. The root layout is `src/app/[locale]/layout.tsx`, and locale comes from `next/root-params` as the next-intl docs recommend for Next ≥ 16.3.
- **English catalog is the typed reference** (`AppConfig.Messages`); a unit test enforces identical keys and no empty strings in `sr.json`.
- **Serbian copy uses the informal "ti"** to match the spec's "speak to ONE person" voice.
- **shadcn/ui on the Radix base (`new-york` style)**, wired to Relay tokens. Radix is the most battle-tested primitives layer for the accessibility bar. shadcn now ships the `cn` helper as its own package (`cn`, maintained by shadcn), which replaces clsx + tailwind-merge.
- **Single light theme for v1, no dark mode.** The spec's direction is explicitly light and warm, and a second theme doubles the contrast surface. The widget themes independently from `brand_color`.
- **Design tokens are hex values in `globals.css`, and a unit test parses them and checks WCAG AA pairs.** Contrast can't silently regress when someone tweaks a color.
- **Fonts: Fraunces (display, `SOFT`/`opsz` axes) + Instrument Sans (UI) via `next/font/google`, `latin-ext` subset.** Serbian Latin diacritics need it.
- **Supabase CLI as a devDependency (`pnpm exec supabase`)** so every machine and CI use the same pinned CLI version.
- **Default models `claude-haiku-4-5` (Free) / `claude-sonnet-5-5` (Pro)**, overridable via env. Re-verify against Anthropic docs in Phase 10.
- **E2E runs against `next start` (a production build)** so CI tests what Vercel serves.
- **`.gitattributes` forces LF.** The repo is developed on Windows and CI runs on Linux.
- **gitleaks runs from the pinned official image (`ghcr.io/gitleaks/gitleaks:v8.30.1`) over the full history**, not `gitleaks-action`. The action failed on the repo's first push (commit-range edge case) and targets deprecated Node 20, while a full scan of a small repo is cheap and has no edge cases.
- **Local development uses Docker Desktop (WSL2) for the local Supabase stack** (`supabase start`). Migrations and RLS tests run against a disposable local database first; the cloud project only receives `supabase db push`.

## Phase 1: Database, auth, RLS

- **Child tables carry `bot_id` next to `conversation_id` with a composite FK to `conversations (id, bot_id)`.** RLS stays one lookup away from the owner (`private.owns_bot`), and a message, action run or ticket can never point at another bot's conversation. `messages.bot_id` and `n8n_outbox.owner_id` are additions to the §6 contract for exactly this reason.
- **Policies call `private.owns_bot(bot_id)`, a `SECURITY DEFINER` helper in a schema PostgREST doesn't expose.** One indexed lookup, no RLS recursion through `bots`, and `(select auth.uid())` is evaluated once per statement.
- **Least privilege by default:** migrations revoke all table and function access from `anon`/`authenticated`, and future objects inherit that via `ALTER DEFAULT PRIVILEGES`. Every grant is explicit and column-scoped for writes. `anon` gets nothing: the widget API runs server-side with the service role.
- **Owners may read `conversations.token_hash` / `realtime_channel` (no column-level SELECT restriction).** They are the owner's own conversations, the hash is useless without the 128-bit token, and column-limited SELECT breaks `select *` and Realtime `postgres_changes` (Phase 6).
- **`start_conversation` enforces the quota with one `INSERT … ON CONFLICT DO UPDATE … WHERE count < limit`.** The conflict row lock serializes concurrent callers, so no read-then-write race. The conversation insert is in the same transaction, so a failure rolls the increment back. A test races 20 calls against 5 free slots.
- **`check_rate_limit` is a fixed window** (`floor(epoch / window)`), one atomic upsert per call. Simpler than a sliding window; the worst case of 2× burst at a window edge is acceptable for abuse control.
- **`match_faqs` is `SECURITY INVOKER` (a deviation from the spec's DEFINER list).** The dashboard playground calls it as the owner, so RLS confines it to their bots. The widget calls it with the service role and an explicit bot id.
- **`hnsw.iterative_scan = relaxed_order` on `match_faqs`** (pgvector 0.8). With one global HNSW index, post-filtering by `bot_id` could otherwise return too few rows for a small tenant.
- **Full-text query = OR of parsed lexemes, each `quote_literal`-ed**, so visitor text can never inject tsquery syntax. Diacritic-insensitive matching (`unaccent`) is deferred to Phase 3, where §12 says to measure it.
- **Deleting a conversation cascades to its messages, unknown questions and action runs; tickets keep their row with `conversation_id` set to null.** Privacy for chat content, while tickets remain the owner's business record.
- **Plan limits on bots (Free 1 / Pro 3) are enforced in Phase 2** together with bot CRUD.
- **Integration tests run against the local Supabase stack with real clients** (signed-in users via the publishable key, the service role via the secret key), not pgTAP. The same TypeScript helpers are reused by later phases. The runner refuses non-local API URLs.
- **Auth uses Server Actions + `@supabase/ssr`; identity comes from `getClaims()`** (verified JWT), never `getSession()`. `requireUser()` runs in every protected component and action; the proxy redirect is a convenience, not the guard.
- **The proxy only refreshes sessions on auth-aware paths** (`/dashboard/**`, `/login`, `/signup`, `/forgot-password`), so marketing pages stay static and fast.
- **`await connection()` before creating the session client.** Session-bound rendering is request-time anyway, and it stops Next's prefetch prerender from hitting supabase-js's `Date.now()` expiry check.
- **Forms post `locale` as a hidden field.** `next/root-params` is unavailable inside Server Actions.
- **Email links land on `/api/auth/callback`, which accepts both the PKCE `code` and `token_hash` flows.** A PKCE code can only be exchanged in the browser that signed up. Supabase has already confirmed the address before redirecting, so a sign-up link opened elsewhere (`flow=signup`, exchange fails) now says "email confirmed, sign in" instead of "invalid link". Switching the email templates to `token_hash` would also sign the user in there (optional manual step). Local config enables email confirmations to match the cloud project.
- **Our own per-IP limits on sign-in/sign-up/reset emails** (`check_rate_limit`, HMAC-hashed IP). Auth calls come from the server, so Supabase's per-IP limits would only see Vercel's address. Fails open, with one log line, when `IP_HASH_SALT` or the database is missing.
- **No account enumeration:** sign-up for an existing email and reset for an unknown email show the same "check your inbox" message.
- **The Google button renders only when Supabase reports the provider enabled** (`/auth/v1/settings`, cached for minutes). A disabled provider would otherwise end on a raw JSON error page.
- **Post-login redirects accept only same-origin relative paths** (`safeNextPath`: single leading slash, no backslashes or control characters, URL-parsed origin check).
- **The locale switcher uses full page loads with an explicit prefix (`/en/...`).** Client navigation between locales keeps the old `<html lang>` (wrong screen-reader voice), and an unprefixed URL would be bounced back by the old locale cookie.
- **The saved `ui_language` decides the locale after sign-in**, and changing it in Account switches the dashboard immediately.
- **`--input` darkened to `#958270`** so form-control borders reach 3:1 on every surface (WCAG 1.4.11); the contrast test enforces it.
- **Serbian copy avoids gendered verb forms** ("Drago nam je što si tu", "Zaboravljena lozinka?") because the owner's gender is unknown.

## Phase 2: Dashboard shell and bots

- **The bot plan limit lives in a `BEFORE INSERT` trigger with a per-owner advisory lock.** No code path (dashboard, a future API, the sandbox seeder) can skip it, and parallel creates can't both pass the count. A test fires 6 concurrent inserts at a Free account and gets exactly 1. The UI's "limit reached" state is display only.
- **Logos live in a public `bot-logos` bucket**, because the widget renders them on third-party sites. Bucket settings cap size at 200 KB and MIME at PNG/JPEG/WebP; storage RLS allows writes only under `<bot_id>/` for bots the owner owns. The Server Action also checks magic bytes, so a renamed SVG never reaches storage.
- **Every logo upload gets a fresh random file name**, and the previous object is deleted. No cache-busting query strings, and long `Cache-Control` is safe.
- **Allowed origins are normalized by one shared function on both client and server** (scheme + lowercase host + non-default port, path dropped, IDN to punycode). http is accepted only for localhost/127.0.0.1. Duplicates after normalization are rejected rather than merged silently. A unit test checks the output against the same regex as the DB constraint.
- **Quick questions are `[{ language, text }]`, at most 3 per language.** The widget shows the chips for the visitor's language.
- **List editors post their state as JSON hidden fields**, validated by zod on the server like every other field.
- **The bot editor is fully controlled**, so the live preview follows every keystroke and a failed submit keeps the draft. The preview is a static mock marked `inert` (looks real, takes no focus); Phase 5 replaces it with the real widget.
- **The preview's text color comes from `readableForeground(brand_color)`** (white or ink, whichever contrasts more). A test sweeps the color space and asserts ≥ 3:1 everywhere; the widget will use the same function.
- **Bot ids in URLs are validated as UUIDs before querying.** Someone else's bot is invisible through RLS and renders the same "not found" as a missing one.
- **The sidebar collapses into horizontal tabs below `lg`.** URL-reading client components (nav, locale switcher) sit behind Suspense, which Cache Components requires once a dynamic segment (`bots/[botId]`) exists.
- **E2E reloads after client redirects before asserting.** Next keeps the previous route mounted but hidden (Activity) for back navigation, so the old form is still in the DOM.

## Phase 3: Knowledge and retrieval

- **The `embed` Edge Function is pure compute (text in, vectors out) and never touches the database.** The Next.js server calls it with the project's secret key and writes vectors itself, because embedding columns are service-role only. One function then serves FAQ indexing, playground queries and (Phase 4) widget queries.
- **The function authenticates with `@supabase/server` `withSupabase({ auth: "secret" })`, `verify_jwt = false`.** This is Supabase's current guidance for the new API keys: `sb_secret_` keys aren't JWTs, so the gateway's JWT check can't validate them. Consequence: `SUPABASE_SERVICE_ROLE_KEY` must hold the new secret key, not the legacy service-role JWT.
- **Batches of 8 texts per request (function cap 16), split in half and retried on status 546.** gte-small costs about 0.1 s of CPU per text locally and a request gets roughly 2 s of CPU; 16 already tripped the limit. Input is capped at 2,000 characters per text (the model reads 512 tokens anyway).
- **FAQs are embedded by their question only.** The eval compared question vs question + answer: question-only ranks better for English, which is where the model is reliable (see the report).
- **Indexing runs inline in the Server Action that saved the FAQ; a failure leaves `embedding_status = failed`, never a fake vector.** The owner sees the status and a "Re-index all" button. A vector is written only if the row's `updated_at` is unchanged, so an edit made during embedding can't receive a stale vector.
- **Diacritics are folded for full-text search (`unaccent`, đ→dj) in a generated `fts` column, question weighted A and answer B.** For vectors folding changes nothing: gte-small's uncased tokenizer already strips accents, and the eval shows identical numbers with and without it. `public.search_normalize` mirrors the app's `normalizeForSearch`, and a DB test checks they produce the same words.
- **Text query = content words minus an EN+SR stop-word list, OR-ed; words over five letters match as a prefix without their last two letters** ("povraćaja" → `povrac:*`). A crude stemmer, but Serbian case endings otherwise never meet. Lexemes are still `quote_literal`-ed.
- **`match_faqs` gained `p_language` and returns `keyword_overlap`** (share of the query's content words found in the FAQ's question). The old five-argument signature was dropped. Retrieval always filters to the visitor's language.
- **Answering rule: the top match's similarity must clear a threshold, or a lower one when ≥ 50% of the keywords also appear in that FAQ's question. Settings are per language.** gte-small is English-only: Serbian similarities crowd into 0.83–0.93 for related and unrelated questions alike, so one global cosine threshold either answers nonsense or nothing. Keyword corroboration took Serbian false accepts from 83% to 0% on the golden set.
- **Shipped settings: EN vector-only, 0.88 / 0.80; SR hybrid (RRF), 0.91 / 0.895.** Picked by the eval's search for the most correct outcomes with false accepts and confidently wrong answers each ≤ 10%. Hybrid hurts English ranking (top-1 84% → 76%) but lifts Serbian (top-1 68% → 79%, top-3 76% → 89%). The thresholds were tuned on the golden set itself, and the report says so.
- **When the bot declines, the top three questions come back as "did you mean" suggestions.** Serbian top-3 is far better than its confidence signal, so suggestions recover much of what the strict threshold declines. The playground shows them; the widget turns them into chips in Phase 5.
- **Retrieval targets, honestly:** EN top-1 is 84.2% (target 85%, missed by one query); SR top-1 is 68.4% vector-only (missed), 78.9% with hybrid (met, so hybrid is on for Serbian); false accepts are 0% in both languages. The cost of 0% false accepts is that the bot answers only 58% (EN) and 37% (SR) of in-scope questions on its own. The gap is the model; a multilingual embedding model would need an external API, which the $0 rule rules out.
- **Ties are broken by vector distance, then id, in both the text ranking and the fused order.** Equal text scores and equal RRF sums are common, and breaking them by a random UUID made the Serbian numbers move by ±5 points between eval runs.
- **`pnpm eval:retrieval` runs against the local stack only, through the real `embed` → `match_faqs` → `decideAnswer` path**, with a throwaway owner that is deleted afterwards. It runs through `tsx` (new dev dependency) so scripts share the app's TypeScript modules.
- **The Kroj demo FAQ set lives in `src/lib/demo/kroj-faqs.json` from now on** (25 EN + 25 SR, same keys in both languages). The golden set labels answers by those keys, and Phase 9 seeds the demo bot from the same file.
- **The playground runs as the owner (RLS-scoped `match_faqs`), limited to 30 questions a minute per owner**, because each question calls the embed function. When embedding is unreachable it falls back to keyword search and says the bot would not answer.
- **Up to 300 FAQs per bot and 100 per import**, checked in the Server Action (a soft cap; a race past it is harmless). The import parser accepts `Q:/A:` and Serbian `P:/O:` and reports problem lines instead of guessing.
- **Language detection is a small heuristic** (Serbian diacritics, then common EN/SR function words; ties go to the bot's default language). Good enough to route between two languages; the widget's locale wins when it is known (Phase 4).
- **Form results that unmount their own form (starter set, delete) report through a parent that stays mounted.** A successful action revalidates the page in the same transition, so the empty state or the deleted row disappears before its effect could show the message.
- **CI's local stack still starts without the Edge runtime**, so CI e2e covers the "not indexed" path, while local runs (`pnpm db:start:embed`) cover real indexing. The model download (about 130 MB from Hugging Face on every runtime start) would add minutes and a network dependency to every CI run.

## Phase 4: Conversation engine and public API

- **Each step of a widget turn is one atomic SQL function, service role only:** `start_conversation` (quota), `add_visitor_message` (the 20-message cap sits in the UPDATE's WHERE clause, so parallel requests can't exceed it; a test fires 12 at 5 free slots and gets exactly 5) and `record_bot_reply` (reply, unknown streak, first-response time and the `unknown_questions` row together). No read-then-write in app code.
- **The bot's reply is saved before it is streamed.** A visitor who closes the tab mid-answer still sees the whole reply after a refresh, and a failed save ends the stream with an `error` event instead of a reply that was never stored.
- **Errors before the stream starts are JSON with a status code; failures after it are an SSE `error` event.** `curl` and the widget both get a clean signal: 400 `bad_request`/`empty_message`/`message_too_long`, 401 `invalid_token`, 403 `origin_not_allowed`, 404 `bot_not_found`, 409 `conversation_closed`, 429 `rate_limited`/`message_cap_reached`/`bot_daily_limit` (with `Retry-After`), 503 `quota_exceeded`/`bot_inactive`/`not_configured`.
- **SSE frames carry JSON on a single `data:` line**, so no content can forge an extra field or event. `meta` carries the token only on a conversation's first message.
- **Sample answers stream in chunks of three words, 25 ms apart.** The same protocol Live mode will use, and fast (about a second for a typical answer). Chunks join back to the exact stored text (unit-tested).
- **The token travels in `X-Relay-Token`, is looked up by its hash within the bot, then re-checked in constant time.** A token from another bot's conversation is indistinguishable from an unknown one (401).
- **Preflights are answered for any origin; the real request is refused with 403 and no CORS headers unless its origin is allowed for that bot.** A preflight has no body, so it can't name the bot, and approving it reads nothing. The app's own origin is always allowed (dashboard preview in Phase 5, demo store in Phase 9). Requests without an Origin header (curl, servers) are allowed: Origin is not abuse protection, the rate limits are.
- **Rate limits (all `check_rate_limit`):** 20 messages per minute and 5 new conversations per 10 minutes per visitor IP and bot, 2,000 messages per bot per day, 30 polls per minute per conversation, 10 rate/end calls per minute per conversation, 60 config reads per minute per IP. IP limits use the HMAC-hashed IP and are skipped (fail open, as in Phase 1) when `IP_HASH_SALT` is missing; the per-bot daily cap always applies.
- **Language per message:** Serbian diacritics or common words decide; otherwise the widget's `locale`, then the conversation's language (or the bot's default for a new chat). The conversation's language follows the visitor's latest message, and retrieval searches that language's FAQs.
- **Three outcomes per turn: answered, unknown, degraded.** Degraded means retrieval itself failed (embedding unreachable): the bot says it can't look things up right now and offers a person, and nothing is logged as an unknown question or counted in the unknown streak, because the bot didn't fail to know.
- **"Did you mean" suggestions only for questions with similarity ≥ 0.80.** Without the floor, "what's the weather" got three random offers.
- **Handoff itself is Phase 6.** For now, an unknown or degraded turn ends with `offerHuman: true` and the streak is counted; Phase 6 adds the `handoff` event and the `waiting_human` status. When a person already handles a chat, the bot stores the visitor's message and stays quiet (`outcome: waiting`).
- **`/api/widget/confirm` and `/api/widget/handoff` don't exist yet** (Phases 7 and 6). No placeholder routes that pretend to work.
- **`selectMode` is real and tested, and returns Sample with reason `live_not_available_yet` until Phase 10 sets `LIVE_MODE_IMPLEMENTED`.** The reason is stored in each bot message's `meta`, so it is visible why a reply was Sample.
- **`/api/widget/end` resolves the chat with `resolved_by = visitor` and is idempotent;** later messages get 409. Analytics (Phase 8) tells bot-resolved from handed-off by `handed_off_at`.
- **Config is cacheable for 30 s (`Vary: Origin`)** and exposes only public settings plus `available` (active and under the monthly quota). An open chat may continue while `available` is false.
- **Route handlers are thin; the logic lives in `src/lib/widget/` and is tested against the local stack** with a fake query embedder (unit vectors), so CI needs no Edge runtime. The DB Vitest config aliases `server-only` to an empty module for this.

## Phase 5: The widget

- **No framework, no runtime dependencies: 9 KB gzipped against the 30 KB budget.** `scripts/build-widget.mjs` (esbuild, IIFE, ES2020) fails the build above 30 KB, and it runs inside `pnpm build`, so CI enforces the budget. The output is git-ignored and rebuilt on every build and `pnpm dev`.
- **The widget doesn't import app code.** It talks to the API only through the documented JSON/SSE shapes, so the bundle stays small and can't pull in server modules by accident. The one shared rule, readable text on the brand color, is reimplemented in a few lines (`foregroundFor`) with the same formula and a test.
- **Isolation: an open Shadow DOM, `:host { all: initial }`, plus inline `!important` styles on the host element.** The host element is the one node page CSS can still target. Inline `!important` outranks any stylesheet, so the page can't hide, move or fade it, and `all: initial` stops inherited fonts and colors. The e2e host page throws `* { … !important }`, `display:none`, `visibility:hidden` and `opacity:0` at it, and the test checks computed styles inside. Open rather than closed mode: closed adds no protection against scripts on the same page, and it would hide the widget from accessibility tooling and Playwright.
- **All text goes through `textContent` or text nodes; the Markdown renderer builds DOM nodes from a whitelist** (paragraphs, line breaks, `**bold**`, `-`/`1.` lists, https links with `target=_blank rel="noopener noreferrer nofollow"`). Only `https:` links without credentials become anchors. The tests feed it `<script>`, `onerror`, `javascript:`/`data:`/`vbscript:` links, attribute break-outs and encoded entities, and assert every produced element and attribute is on the whitelist.
- **While a reply streams, the bubble shows plain text; Markdown is applied once, at `done`.** Half-received `**` or `[link](` never flicker as broken formatting.
- **Screen readers: messages go to one visually hidden `aria-live="polite"` region, announced once per complete reply, with its source label.** Making the message list itself live would read every streamed chunk.
- **The panel is a modal dialog (`aria-modal`, focus trap, Escape closes and returns focus to the launcher).** Focus moves to the input on open. All controls have labels; the launcher's `aria-expanded` reflects the panel.
- **Only the visitor's own conversation token is stored, in `localStorage` under `relay-ai:v1:<bot>:token`.** Blocked storage just means no resume. A stale token (conversation deleted or purged) is dropped silently and the message is resent in a new conversation.
- **New endpoint `GET /api/widget/conversation`** returns the full history (with source labels and Sample flags) so a refresh resumes the chat. `poll` stays limited to new human/system messages, as specified. Same bot + token scoping and rate limit as polling.
- **Widget language: `data-lang` on the script tag, then `<html lang>`, then the browser** (sr/hr/bs/sh/me → Serbian, else English). Replies still follow the language each message is written in.
- **A widget that can't load its config (unknown bot, website not on the list, service down) renders nothing** and logs one console warning for the shop owner. Visitors never see a broken chat button.
- **"Talk to a human" appears in Phase 6, together with handoff.** Until then the bot's "I don't know" reply offers a person in words only; a button that does nothing would be a stub.
- **The dashboard preview is the real `public/widget.js`, mounted inline through `window.RelayAI.preview()` with the draft settings,** isolated in its own shadow root. Sending is off there (the playground is for answers), so the preview never creates conversations or uses up the monthly quota. Opening messages re-render only when the greeting or quick questions change, so typing in the form doesn't flicker the preview.
- **E2E serves a hostile third-party page from a second local server (port 3101)** that embeds the widget with the real snippet. Playwright's `expect` timeout is 15 s, because saving an FAQ in CI waits about 5 s for the gateway to give up on the absent embed function.
